# Запуск, восстановление и отмена

## Хранение

Состояние — `var/state.sqlite3`. Используйте один state directory на инсталляцию. База содержит исходные материалы, ответы моделей и результаты. Обеспечьте права доступа к каталогу средствами ОС; приложения не предоставляют шифрование диска или отдельные аккаунты пользователей.

Для согласованной резервной копии используйте SQLite backup API, а не копирование только основного файла при активном WAL:

```python
import sqlite3
with sqlite3.connect('var/state.sqlite3') as source:
    with sqlite3.connect('backup.sqlite3') as target:
        source.backup(target)
```

Для восстановления остановите процессы сервиса и worker, поместите **проверенную** резервную копию в новый каталог состояния и запустите с `--root restored-state`. Не подменяйте базу под работающим процессом. При запуске применяются миграции user_version: `1` создаёт основные таблицы, `2` добавляет снимок окружения. Неизвестная будущая версия отклоняется.

## Потеря worker

1. Просмотрите `status RUN_ID` и `manifest RUN_ID`.
2. Если процесс погиб, дождитесь истечения lease (до 15 секунд после последнего heartbeat). Живой lease нельзя отнять командой `resume`.
3. Запустите `work --once` или API: записи `queued` и `running` с истёкшим lease будут продолжены автоматически. Команда `resume RUN_ID` также запускает продолжение допустимого состояния.
4. Сохранённые checkpoints и успешные receipts используются повторно. Запросы без известного результата получают статус `unknown` и остаются зарезервированными по полной оценке.
5. Выполните `replay RUN_ID`. `partial` означает, что доступна проверка уже записанных объектов, но финального пакета ещё нет.

Контрактные и транспортные лимиты учитываются по сохранённой истории вызовов. Рестарт не даёт новый лимит. После исчерпания повторов создайте новый run, если решили разрешить новую попытку; старый бюджет и журнал сохраняются. Бюджет и исходную задачу существующего run изменить нельзя.

## Состояния

| Статус | Значение и действие |
| --- | --- |
| queued / running | Очередь / исполнение; worker продолжает после потери lease. |
| waiting_approval | Пакет готов к просмотру. Проверьте `result`/экспорт и передайте его SHA-256 в `approve` или `reject`. |
| completed | Выпуск по разрешённой политике либо приёмка человеком; см. approvals. |
| blocked | Нет допустимого маршрута/инструмента, конфликт версий или внутренняя ошибка. Изменённые входы/права требуют нового run. |
| provider_unavailable | API недоступен, отказ модели или исчерпаны запросы. Resume не обнуляет повторы. |
| validation_failed | План, контракт, цитата, lineage или решение reviewer нарушили gate. Нужен разбор, затем новый run при изменении задачи. |
| rejected | После разрешённых содержательных итераций остались блокирующие замечания или человек отклонил пакет. |
| inconclusive | Reviewer не смог установить основание для приёмки. |
| budget_exceeded | Новый вызов не помещается в бюджет либо известный расход превысил резерв; новые узлы не запускаются. |
| timed_out | Истёк сохранённый deadline. Время ожидания и простоя тоже входит в общий срок исполнения до подготовки пакета. Ручная приёмка готового пакета не продлевает вычисления. |
| cancelled | Отмена окончательна; этот run не возобновляется. |

`waiting_approval`, `completed`, `rejected`, `cancelled`, `validation_failed`, `inconclusive`, `budget_exceeded`, `timed_out` не разрешают `resume`. Для продолжения с другими условиями создаётся новая задача с новым run_id и отдельным бюджетом.

## Отмена

`cancel RUN_ID` атомарно фиксирует намерение и статус. Новые вызовы и фиксация новых артефактов запрещаются. HTTP-вызов, который уже выполняется, может завершиться до transport timeout; его usage сохраняется, но результат не передаётся в следующий узел. Если ответ потерян, reservation остаётся неопределённым расходом. Удалённый провайдер не обязан прекращать генерацию из-за закрытия клиентского соединения.

Python sandbox при сигнале отмены прекращает контейнер. Ни при отмене, ни при недоступном Docker нет запуска кода на host.

## Изменение модели/схем/инструмента

Не редактируйте снимки конфигурации в SQLite. Создайте новую версию конфигурации, прогоните предметный eval и регрессию, затем подавайте новые задачи. Для уже выполнявшихся задач сохранённый config остаётся прежним. Изменение major-модели и включение fallback — явное действие администратора, а не решение LLM.

## Sandbox

На машине с Linux Docker daemon:

```powershell
docker build -t multi-llm-sandbox:local sandbox
$env:RUN_SANDBOX_TESTS='1'
.\.venv\Scripts\python.exe -m pytest -q -m sandbox
```

Для ручного запуска создайте копию demo-конфигурации с `sandbox_enabled: true`; команда `sandbox CODE.py --input input.json` принимает код только из явно указанного локального файла. Перед исполнением image tag разрешается в локальный digest, запрещена автоматическая загрузка образа. Production должен отдельно зафиксировать проверенный digest базового образа, применить gVisor/VM при необходимой модели угроз и проверить реальное ограничение ресурсов.

При поставке Docker daemon был недоступен. Проверка отсутствия host-файлов/секретов/сети и принудительного timeout включена в тесты, но требует указанного интеграционного запуска.
